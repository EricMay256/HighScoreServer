# Handoff: proposal revision and librarian console

Date: 2026-09-02

Status: planning complete enough to draft ADRs; no implementation has started.

## Objective

Add two related vault capabilities:

1. Span-based editing of an existing amendment proposal from the review page. An edit creates a new immutable successor proposal; it never rewrites the filed proposal.
2. A third, human-supervised librarian console that can investigate the vault, discuss work with the user, draft governed changes, and submit those changes only after explicit approval.

The librarian should support:

- Proposing new notes when it finds a genuine coverage gap.
- Suggesting new wiki pages from available notes and gaps in existing coverage.
- Reviewing and revising notes.
- Updating stale wiki pages through the existing compile workflow.
- Suggesting inter-note links as two independently visible directions.
- Reviewing tags and normalizing facets.
- Surfacing promotion candidates and compile-decline decisions for human judgment.
- Running bounded knowledge-health checks for stale pages, uncompiled notes, weak coverage, missing summaries, inconsistent metadata, and likely duplicate or isolated notes.

Execution is interactive-only initially. `Step` advances one bounded transition. `Heartbeat` repeatedly steps up to a fixed limit so pseudo-autonomous behavior can be tested without adding a scheduler, worker, or queue.

## Recommended architecture

Use one application-owned librarian workflow with two swappable runners:

```text
/vault/librarian
        |
        v
Librarian workflow service
  sessions - events - artifacts - invocations
        |
        +-- ExternalMCPRunner --> subscription-backed ChatGPT/Codex/Claude client
        |
        +-- ProviderAPIRunner --> OpenAI provider initially; Anthropic adapter later
        |
        v
Read and draft capability layer
        |
        v explicit human approval
Existing contribute - propose - compile - review services
```

The environment chooses the default runner for new sessions:

```text
VAULT_LIBRARIAN_RUNNER=external_mcp

# or
VAULT_LIBRARIAN_RUNNER=provider_api
VAULT_LIBRARIAN_PROVIDER=openai
VAULT_LIBRARIAN_MODEL=<explicit-model-id>
VAULT_LIBRARIAN_API_KEY=<server-side-secret>
```

Each session snapshots its runner, provider, and model. Changing environment configuration affects new sessions only; an in-progress provider conversation cannot silently resume through a different backend.

The default should be `external_mcp`, because ChatGPT and Claude consumer subscriptions do not include backend API billing. The website cannot programmatically wake a consumer chat subscription: it queues work, and the user invokes the external agent connected to the vault MCP server. The provider API runner is optional and separately budgeted.

References:

- OpenAI: https://help.openai.com/en/articles/9039756
- Anthropic: https://support.claude.com/en/articles/9876003-i-have-a-paid-claude-subscription-pro-max-team-or-enterprise-plans-why-do-i-have-to-pay-separately-to-use-the-claude-api-and-console

## Repository facts that constrain the design

The schema audit changed several parts of the earlier proposal.

### Proposal states are separate

`vault_review_cases` has `pending`, `accepted`, `rejected`, and a deliberately reserved `superseded` state. Current code refuses to decide a review case as superseded.

`vault_amendment_proposals` independently has only `pending`, `accepted`, `rejected`, and `stale`. The reserved review-case value is not a reusable amendment-proposal state.

Initial recommendation:

- Add nullable `revises_proposal_id` to the successor amendment proposal.
- Keep the predecessor in the existing state machine: settle it as `rejected` only after the successor exists, with a decision note explaining that it was replaced.
- Derive `revised_by` through the reverse relationship rather than storing two columns that can disagree.
- Add an amendment-specific `superseded` state later only if queueing, reporting, or review semantics prove that `rejected` plus machine-readable lineage is inadequate.

Whether `revises_proposal_id` should be a self-foreign-key or an unconstrained durable correlation is an ADR decision. A foreign key gives stronger lineage integrity; a correlation ID matches the vault's preference for history that can outlive its subject.

### Existing revision and workflow primitives must be reused

- `vault_documents.content_revision` is the optimistic-concurrency token for note drafts, wiki sources, and stale-artifact detection.
- `vault_compile_runs` already owns compile lifecycle and provenance. Librarian state may reference a compile run but must not duplicate or repurpose its state or frontier JSON.
- `vault_documents.compile_declined_at` already represents the judgment that a note need not be compiled. The librarian should surface the existing decision path.
- `vault_documents.promotion_status` already provides `candidate`, `promoted`, and `retracted`. The librarian may recommend promotion work, but it must not make review decisions.
- `vault_write_requests` provides the correct principal-scoped idempotency pattern but is contribution-specific and must not become a generic invocation ledger.

### Audit correlation already has a home

`vault_audit_events` has an indexed `trace_id` that currently appears unused. Set it to the librarian session UUID for every governed action. Use `request_id` for an individual step, heartbeat request, or approval submission.

Audit events remain append-only security history; they do not replace librarian session, artifact, or invocation state.

### Related/source arrays remain authoritative

`related_ids` and `source_ids` intentionally permit dangling references. Existing ADRs defer a typed edge table and identify two narrower additions when reverse lookup becomes necessary:

- GIN indexes on `related_ids` and `source_ids`.
- A bounded batch-fetch operation for known document IDs.

Use those for paired-link suggestions, source inspection, and backlinks. Do not add an open-ended neighbor/traversal endpoint or normalized edge table without measured requirements beyond the existing array design.

### OAuth scopes are duplicated in database constraints

The OAuth schema separates baseline authorized scopes from privileged operator entitlements. Adding librarian scopes requires coordinated changes to credentials, authorization codes, refresh tokens, grants, constants, CLI behavior, and schema-drift tests.

Proposed placement:

- `vault:librarian`: baseline scope for operating one's own sessions, feedback, artifacts, and approvals.
- `vault:librarian-run`: narrow external-runner scope for claiming and returning draft work.
- `vault:compile`: remains a privileged operator entitlement used by the human approval path, not by the model.

This placement must be confirmed in the authorization ADR before migration work.

### Documentation drift found during the audit

- An older ADR mentions `proposed_doc_type`, but no such live column or workflow exists. Do not design against it; use the implemented promotion-status workflow.
- A compile-domain comment still suggests future plans compare stored frontiers. The current planner uses per-document state, including `compile_declined_at`; run frontiers are historical provenance.

## Security and governance invariants

- The model may read governed knowledge and create librarian drafts. It never receives corpus-commit, review, update, or delete capabilities.
- Capability restriction is enforced by the server-generated tool list, not only by a prompt.
- Notes and wiki pages are untrusted model input.
- Human approval invokes the existing application services:
  - New note -> contribution and deduplication.
  - Note revision -> immutable amendment proposal.
  - Wiki page -> compile write.
  - Links/facets/source metadata -> metadata amendment proposal.
  - Title/tags/aliases/body -> full amendment and re-embedding where applicable.
- The librarian never receives `vault:review`.
- Editing a formal proposal creates a linked successor and preserves the original.
- Every draft records the source document IDs and `content_revision` values used.
- The workflow service, never the model, creates and persists idempotency keys.
- There is at most one in-flight invocation per session.
- No hidden chain-of-thought is stored. Persist user-visible messages, concise tool summaries, decisions, evidence, errors, provider identifiers, usage, and cost.

## Phase 1 - Span-based proposal tweaking

Implement this independently of model integration.

### Browser flow

1. Reviewer opens a pending amendment proposal.
2. The review page materializes its resulting body.
3. Reviewer selects and edits a span.
4. The page previews the adjusted result and canonical diff against the current target note.
5. The complementary proposer credential files a new immutable proposal with `revises_proposal_id`.
6. After successor creation succeeds, the reviewer credential rejects the predecessor with a replacement decision note.
7. The successor remains pending for an explicit review decision.

The current repository does not yet implement the complementary proposer credential on the review page; ADR 0039 explicitly deferred reviewer-side editing. Phase 1 must add that browser flow rather than assume it exists.

Body-only edits should derive the strictest canonical amendment from the adjusted result. Metadata proposals use structured controls instead of pretending facets or links are text spans. Touching title, body, tags, aliases, or other embedded fields requires the full replacement form and re-embedding.

### Failure handling

The two credentials mean this is not one database transaction:

- If successor creation fails, the predecessor remains pending.
- If successor creation succeeds but predecessor settlement fails, expose a recoverable `successor filed; finish settlement` UI state.
- Never settle the predecessor before the successor exists.
- Refuse if the target document revision changed; do not silently rebase.
- A retry must replay or discover the already-created successor rather than create another.

This phase requires an Alembic revision for proposal lineage, plus API models, repositories, services, review template/JavaScript, and tests.

Checkpoint: manually exercise body replacement, metadata amendment, removal acknowledgement, stale target, duplicate retry, and interrupted two-step recovery.

## Phase 2 - Librarian workflow persistence and authorization

Create workflow state separate from the document corpus. One Alembic revision should introduce approximately four tables:

### `vault_librarian_sessions`

- Owner principal.
- Runner/provider/model snapshot.
- Goal and workflow state.
- Monotonic workflow revision for compare-and-set.
- Active provider response identifier when applicable.
- Optional associated compile-run ID.
- Created, updated, and completed timestamps.

### `vault_librarian_events`

- Append-only user messages, visible assistant messages, tool summaries, transitions, and errors.
- Session-local sequence number.
- Step/request correlation.
- No hidden model reasoning.

### `vault_librarian_artifacts`

- Versioned drafts.
- Kinds: note contribution, note amendment, wiki page, metadata amendment, and one direction of a paired link.
- Source/target IDs and their base revisions.
- Draft payload, rationale, evidence, and preview data.
- States such as draft, approved, submitted, rejected, and stale.
- Submitted document, proposal, or page identifiers.

### `vault_librarian_invocations`

- Runner step and provider request identifier.
- Status, token usage, estimated cost, and pricing snapshot.
- Started/completed timestamps.
- Application-minted idempotency data.

Keep invocations typed rather than folding them into event JSON because the sub-$5 budget requires reliable aggregation and reservation queries.

All governed actions write normal audit events using `trace_id=session_id`; do not duplicate the full audit record in these tables.

Checkpoint: verify session ownership, cross-principal refusal, compare-and-set behavior, single-invocation enforcement, tool filtering, idempotent retries, and audit correlation.

## Phase 3 - Third console and provider-neutral workflow

Add `/vault/librarian` using shared OAuth/session infrastructure and a distinct browser-storage namespace.

Console areas:

- Session list and new-request action.
- Conversation and feedback panel.
- Sources panel showing each fetched document and revision.
- Draft workspace with per-artifact status and diff/structured previews.
- Invocation and cost status.
- Explicit `Give feedback`, `Regenerate`, `Approve and submit`, `Reject draft`, `Step`, `Heartbeat`, and `Cancel session` actions.

Feedback edits librarian artifacts, not formal amendment proposals. Only `Approve and submit` invokes a governed write/propose/compile adapter.

Provide structured starters without restricting free-form requests:

- Review or revise notes.
- Compile or update a wiki page.
- Fill a coverage gap with a new note.
- Suggest related-note links.
- Normalize facets or review tags.
- Review promotion candidates.
- Run a knowledge-health audit.

Checkpoint: complete a mocked end-to-end conversation without contacting a model provider.

## Phase 4 - Zero-incremental-cost external MCP runner

Make `ExternalMCPRunner` the default. Add scope-gated MCP operations for listing work, reading a session, claiming one step, recording progress, submitting structured artifacts, and finishing a step.

The external agent receives only:

- `vault:read`
- `vault:librarian-run`

It cannot contribute, propose, compile, review, update, or delete. The website queues a step and displays a copyable instruction, for example:

```text
Heartbeat librarian session <id> for at most 5 steps.
```

`Step` claims and completes one bounded transition. `Heartbeat` processes at most N transitions and stops when user feedback, artifact approval, a limit, completion, or an error is reached.

Changing the MCP surface also requires updating and distributing the matching `knowledge-vault` skill in the private knowledge-platform repository. Server/skill agreement and per-client distribution are separate release obligations.

Checkpoint: run equivalent sessions from supported subscription-backed clients connected to the MCP server. Client support must be verified at implementation time rather than assumed from a subscription name.

## Phase 5 - Artifact approval adapters

Runners return provider-neutral structured artifacts. Application-owned adapters perform approved actions with the human console credential.

### Note amendment

- Require `note_id` and `base_revision`.
- Show current content, proposed content, canonical diff, rationale, and evidence.
- Submit through the existing amendment service.
- Return stale drafts to feedback/regeneration.

### New note

- Require title, body, summary, tags, aliases, facets, and supporting source IDs where applicable.
- Submit through contribution/deduplication.
- Treat inserted, flagged, rejected, and invalid as settled outcomes.
- Link flagged contributions to the review console; never automatically retry them.

### Wiki page

- Open or attach to a normal compile run.
- Use its missing, stale, and new-source work items.
- Record every source ID and `content_revision` in the artifact.
- Check expected source revisions under the corpus lock before writing.
- Write one page only after explicit approval.
- Finish only after selected work is written or explicitly declined through the existing compile-decline path.
- Cancelling the librarian session fails the active compile run while preserving already-approved pages.

### Paired links

Produce two independently selectable metadata artifacts:

```text
A.related_ids += B
B.related_ids += A
```

Each direction has its own rationale, preview, proposal, and decision. Add bounded reverse lookup and batch fetch; add GIN indexes when query measurements justify them. Do not add generalized graph traversal.

### Tags and facets

- Facets use sparse metadata proposals and require no embedding refresh.
- Tags use full amendments because they affect embedded text, retrieval, and deduplication.
- Bulk maintenance is a collection of independently reviewable artifacts, not one opaque mutation.

### Promotion and compilation recommendations

- Promotion suggestions remain recommendations for a credential with `vault:review`.
- Compile-decline suggestions invoke the existing decision only after human approval.
- Do not invent parallel librarian states for either workflow.

Checkpoint: demonstrate every artifact path with provider calls mocked.

## Phase 6 - Optional provider API runner

Keep runner selection separate from provider selection:

```python
class LibrarianRunner(Protocol):
    async def step(self, ...) -> RunnerStepResult: ...


class LibrarianModelProvider(Protocol):
    async def start_response(self, ...) -> ProviderResponse: ...
    async def poll_response(self, ...) -> ProviderResponse: ...
    async def submit_tool_results(self, ...) -> ProviderResponse: ...
```

Initial adapters:

- `ExternalMCPRunner`
- `ProviderAPIRunner`
- `OpenAIResponsesProvider`
- Later, `AnthropicMessagesProvider`

Switching OpenAI/Anthropic changes `VAULT_LIBRARIAN_PROVIDER`; switching between direct API and subscription-backed execution changes `VAULT_LIBRARIAN_RUNNER`.

Prefer existing async `httpx` for the first provider adapter to avoid adding a dependency. Reconsider an official SDK only if manually maintaining the provider protocol becomes materially larger or less reliable. Any provider call must remain async and must never block FastAPI's event loop.

### Cost controls

- Hard application ceiling of USD $5 per calendar month; environment configuration may lower but not raise it.
- Dedicated provider project/key or equivalent billing boundary.
- Provider-side spend/prepaid controls where supported.
- Reserve worst-case estimated cost before starting an invocation.
- Per-step output-token ceiling.
- Per-session token, invocation, and step ceilings.
- Per-heartbeat step ceiling.
- No automatic retry for billing refusal.
- Persist provider-reported usage and the pricing snapshot used for estimates.
- Show month-to-date reserved and settled estimated spend.
- Release unused reservation after a terminal response.
- Default remains `external_mcp`.

Pricing and provider limit behavior are time-sensitive and must be verified against official documentation when this adapter is implemented.

Checkpoint: test against a deliberately tiny prepaid/provider limit and verify application refusal before its own ceiling.

## Phase 7 - Bounded pseudo-autonomy

Implement heartbeat as a client-driven loop over step:

```text
repeat up to N:
    POST /sessions/{id}/step
    poll only while provider work is pending
    stop at feedback, approval, completion, cancellation, error, or budget limit
```

Required properties:

- Cancellable between steps.
- One in-flight invocation per session.
- Row lock or compare-and-set on workflow revision.
- Safe resumption after browser refresh.
- No sleeping task inside a Gunicorn worker.
- No recurring scheduler, new Heroku process, or queue.

Checkpoint: interrupt every transition and verify idempotent recovery.

## Phase 8 - Verification

The evaluation corpus should cover:

- Editing an existing proposal and preserving its predecessor.
- Recovery between successor creation and predecessor settlement.
- Suggesting a wiki page from uncovered notes.
- Updating a stale wiki page.
- Declining irrelevant compile sources through existing state.
- Contributing a real coverage-gap note.
- Duplicate and near-duplicate contribution outcomes.
- Independent paired-link directions and backlinks.
- Facet cleanup versus tag cleanup.
- Promotion recommendations without model adjudication.
- Stale target and source revisions.
- Prompt injection inside documents.
- Attempts to obtain commit/review/update/delete operations.
- Budget exhaustion, provider outage, and runner parity.
- Session trace and request audit correlation.

Verification includes focused service/repository tests, browser behavior tests, MCP visibility tests, migration upgrade/downgrade tests, schema-drift tests, vault boundary/extraction tests, `./scripts/lint.sh` or `.\scripts\lint.ps1`, and full pytest where PostgreSQL is configured.

## Explicitly deferred

- Scheduled or unattended compilation.
- Heroku worker/dyno or new queue infrastructure.
- Self-hosted model inference.
- Model acceptance/rejection of amendment or review cases.
- Automatic reciprocal links.
- Automatic tag rewriting.
- Typed edge table or generalized graph traversal.
- Multiple agents concurrently operating one librarian session.
- Web search by the librarian; the first release works from governed vault content.
- Additional external model providers beyond the first OpenAI adapter and planned Anthropic adapter.

## Open decisions before implementation

1. Should `revises_proposal_id` be a self-foreign-key or a non-FK durable correlation?
2. Is `rejected` plus linked successor sufficient for the predecessor, or does amendment-specific `superseded` have proven UI/reporting value?
3. Does `vault:librarian` belong in baseline authorized scopes, while `vault:librarian-run` remains a separately issued runner capability?
4. Are invocation rows retained indefinitely for accounting/audit, or summarized and pruned after a defined period?
5. Which provider/model pair is acceptable for the first sub-$5 API experiment after checking current prices?
